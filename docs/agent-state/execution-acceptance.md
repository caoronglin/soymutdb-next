## 2. Remaining `apps/web` typecheck — 13 pre-existing errors (NOT contract-generated) ⚠️

Contrary to the hope that regenerating the client would zero it, `apps/web` still
has **13 errors** (down from the baseline 14). Root cause is a **handwritten
api-client ↔ web-UI mismatch**, not the generated `openapi.d.ts`:

1. **Federated search type missing** (5 errors in `search.tsx`): the backend
   `/search` endpoint fully supports federated external search (`sources` →
   `sources[{source,status,health,error,hits}]`), and `apps/web/src/routes/search.tsx`
   consumes `FederatedSearchResponse`/`sources`/`hits`. But the handwritten
   `packages/api-client/src/search.ts` only exports the internal `SearchResponse`
   (`results`/`by_type`) — `FederatedSearchResponse` is **not exported**. This is a
   missing api-client surface (the type is not in the generated file because the
   federated path returns `text/html` fragments / a separate JSON shape not captured
   by the single `/search` response_model).
2. **Pagination mismatch** (6 errors in `blast.tsx` / `genes/index.tsx` /
   `variants/index.tsx`): the handwritten client migrated to cursor pagination
   (`cursor`/`limit`/`next_cursor`/`has_more`/`total_count`), but these web routes
   still send `page`/`page_size` and read `total`.
3. **`login.tsx` RouterState cast** (1 error) and `search/genes.tsx` `total` (1 error).

All 13 are pre-existing at HEAD (none in the working tree's Phase 2-4 diff; e.g.
`apps/web/src/routes/search.tsx` is unmodified). They are orthogonal to the
OpenAPI regeneration and require a follow-up: wire `FederatedSearchResponse` into
the api-client `search.ts`, and reconcile page-based callers with the
cursor-based client (or vice versa).
