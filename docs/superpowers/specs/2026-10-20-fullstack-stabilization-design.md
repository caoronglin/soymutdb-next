# SoyMutDB 全线稳定性修复设计

## 已批准的范围

用户要求使用 mm 的 MiniMax 子代理处理 BUG、功能异常、UI/UX、功能衔接与后续扩展接口，并迭代项目依赖。用户随后要求先保存基线，再开展修改；已创建 Draft PR #26（https://github.com/caoronglin/soymutdb-next/pull/26），快照提交 `57e2bcdee3bab3435578997dba85cf26c3b985bc`，其工作区干净。

用户选择“按分批兼容修复方案实施”：保留架构、逐条修复；先处理 BLAST/JBrowse 的 release 传递与现有搜索分页，再补株系检索/分页和新闻跨站预览；扩展沿用现有 API/client/能力门禁。重大接口或不兼容升级另行确认。

## 架构与数据流

- PostgreSQL 继续作为身份、关系、工作流、发布、变异和分析数据的权威库；不引入新存储，不重启历史 ClickHouse 运行路径。
- API/OpenAPI 为契约源；共享客户端、缓存键、门户、管理端、JBrowse 和 Worker 消费同一契约。扩展优先接入现有服务/能力注册，不增加第二套请求或任务框架。
- external/internal、public_id/internal_id、v4/v5、release/assembly 的安全边界不可放宽。上下文缺失时保持安全错误，不使用猜测的 assembly 或随意切换 release 兜底。

## 第一批交互修复

1. BLAST 命中链接必须携带与结果相容的 release/assembly；JBrowse 的 assembly 解析与轨道配置请求必须使用相同 release。没有可信上下文时禁用链接或展示明确可恢复状态，不移除浏览器上下文门禁。
2. 全局搜索消费已有 next_cursor/has_more，提供上一页/下一页和实体类型过滤；查询、过滤、assembly、release 改变时不能复用旧游标。保留 URL 深链；内部目录没有分页契约时不伪造分页。
3. 株系检索与文案必须一致，超过单页数量的结果可达。优先以兼容新增参数实现，不破坏现有 mutagen 精确过滤、公开身份或响应形状。
4. 新闻预览必须导航到明确的门户 origin；未配置时清晰提示，不将带预览令牌的链接发送到猜测 origin。复用现有部署配置所有者，不将 API JSON 预览地址误当成门户 HTML 页面。

## 依赖与扩展

- 实际查询 registry/锁文件并检查现有 ADR 的兼容性决定；优先修复已知漏洞及同主版本更新。
- 更新声明和锁文件作为一个整体；不弱化供应链、许可证、扫描或固定工具链门禁。
- 扩展接口只在已确认断链需要时增加；未知能力不得用空实现、默认成功或静默回退冒充完成。

## 验证与交付

每个发现先追溯根因并确认当前代码未修复，再做最小修复并补回归。覆盖用户可见链路、错误恢复、上下文切换与负向泄漏；影响 API 时验证 OpenAPI/client，涉及数据库时使用隔离 PostgreSQL。资源受限采用低并发定向测试，再跑对应根质量门禁。浏览器或真实服务证据缺失时明确注明，不把单测或构建当作完整体验验证。

修复在 `fix/fullstack-stabilization-20261020` 增量分支进行，由主代理审查、验证与提交；基线分支保持冻结。独立子任务写范围不重叠；子代理不执行 git 生命周期操作。完成报告列出具体修复、精确命令/结果、未覆盖风险及后续事项，不宣称消灭所有潜在 BUG。
