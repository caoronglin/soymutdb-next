# Phase 1.5 · 容量基线（Gate-0，优化前）

> **父计划：** `plan.md`（主路线图）。
> **前置：** Phase 1 已退出（S 组完成，含 S-2 的 `benchmark_mode` 与 `rate_limit_enabled` 分离）。
> **必须早于：** Phase 2 与 Phase 3 的任何优化改动。
> **Wave：** W1.5
> **退出判据：** §3

---

## 0. 为什么单独成阶段

三轮审计反复指出同一个时序错误：v1–v3 把 P1/P2 放在 Phase 4，而 Phase 2（字体/SW）
与 Phase 3（检索索引、排名、预聚合、查询预算）已完成 —— 于是 P1 测到的是**优化后**结果，
Phase 4 的 P6「同参数复测」无从比较，Rust Gate-1 也就失去依据。

因此 P1/P2 从 Phase 4 移出，成为 Phase 1 与 Phase 2 之间的独立门。

```text
Phase 1（安全收口）
   → Phase 1.5（P1/P2 优化前基线）   ← 本文件
   → Phase 2（前端）→ Phase 3（检索/DB）
   → Phase 4（P6 同参数复测 + Gate-1 判定 + 治理）
```

Phase 4 的 P6 **只做复测**，不再承担「建立基线」的职责。

## 1. 任务清单

### P1 · 后端容量基线

**Files:** `tests/load/api-load.js`（扩展）、新增 `scripts/perf-baseline.sh`、新增 `docs/ops/perf-baseline-2026-09-15.md`
**依赖：** Phase 1 S-2 已完成（提供 `benchmark_mode` 与 `rate_limit_enabled` 两个独立开关）

**Steps:**
1. `scripts/perf-baseline.sh backend` 必须满足：
   - **直连 API**（容器网络内的 `http://api:8000`，不经 nginx / tunnel-origin），
     从而绕过边缘 `limit_req`；
   - **同时**关闭应用层通用读限流：`SOYMUTDB_BENCHMARK_MODE=1` **且**
     `SOYMUTDB_RATE_LIMIT_ENABLED=false`。
     S-2 的约束保证这两个值只在 `app_env != prod` 时生效，生产设置即 fail-fast；
   - **断言基线中 429 计数为 0**；若出现 429 立即 `exit 1` 并提示
     「限流未关闭或边缘未绕过，基线无效」。
2. 场景覆盖**公开读**端点，并按端点类别分别统计（与 §2 的 SLO 分类一致）：
   - 详情/检索类：`/api/v1/search`、`/api/v1/genes`
   - 变体列表类：`/api/v1/variants`（带过滤）、`/api/v1/variants/region`
   - 聚合类：`/api/v1/stats/*`、`/api/v1/releases`
3. 并发梯度 50 / 200 / 500 VU；每档记录每个**端点类别**的 RPS、p50/p95/p99、错误率，
   以及 API 容器 CPU、PG 活跃连接、CH 查询 P95。
4. 记录数据量与派生指标（供 Phase 3 的 D6 与 P4 使用）：
   - `variants` / `genes` / `mutant_lines` 行数；
   - **每 Mb 的 variant 行数**（用 D6 的 10 Mb 窗口实测）；
   - 当前「全量变体浏览」一次请求的 CH `read_rows`（P4 的目标基线）。
5. 记录机器规格与容器资源上限（`API_CPU_LIMIT` / `API_MEMORY_LIMIT`）。
6. 声明**采集方式局限**：单机 k6、与本项目生产网络不同、不含 CDN 效应。

**Verify:**
```bash
bash scripts/perf-baseline.sh backend   # 需完整 release 数据 + Docker
# 脚本自检：429 计数必须为 0，否则 exit 1；429 > 0 时不得产出报告
```
**Accept:** `docs/ops/perf-baseline-2026-09-15.md` 入库，含：
零 429 证明、按端点类别的三档数据、数据量与每 Mb 行数、
全量浏览的 CH `read_rows` 基线、机器规格、采集局限声明。

### P2 · 公网防滥用基线（P2a 在本阶段；P2b 在 Phase 4）

**Files:** `scripts/perf-baseline.sh`（`public` 子命令）、`docs/ops/perf-baseline-2026-09-15.md`（续写）
**依赖：** Phase 1 S-3（Tunnel 限流）与 Phase 2 D1（边缘配额）——**但本阶段早于 Phase 2**

> **时序说明（必须遵守）：** Phase 2 的 D1 定义边缘配额，而 P2 要验证配额生效。
> 因此 P2 拆成两个可独立执行的部分：
> - **P2a（本阶段执行）**：验证 **Phase 1 S-3 已建立的 Tunnel 限流 zone** 生效
>   （auth / API 两类），即「公网路径至少有一层限流」。
> - **P2b（Phase 4 执行）**：验证 **Phase 2 D1 的分级配额**（100 r/s / 10 r/s / 1 r/s）。
>
> 本文件只定义 P2a；P2b 的判据在 Phase 4 与 Phase 2 D1 的 Accept 中。

**Steps（P2a）：**
1. 经 `tunnel-origin` 或其本地等价入口发压（不经自建 nginx 的 `proxy_cache` 路径）；
2. 限流**保持开启**；
3. 验证：超限返回 429 且带 `Retry-After`；`/health` 全程 200；
   Range 路径（`/data/`、`/jbrowse-data/`）按连接数限流，不被请求频率误伤。

**Verify:**
```bash
bash scripts/perf-baseline.sh public   # 需 Docker
# 断言：429 计数 > 0（限流确实生效）；/health 全程 200；Range 路径未出现 429
```
**Accept:** P2a 结果写入基线报告；429>0 与 `/health` 200 均有证据；
为 Phase 4 的 P2b 保留同一脚本入口。

## 2. Gate-1 的判据（本阶段只记录，不判定）

三轮审计指出 v1–v3 直接用 `p95 < 300ms`、`CPU < 60%` 是**无依据的魔法值**：
现有生产告警阈值是 `ApiHighP95Latency > 1s`，而计划却要求 300 ms，两者从未对齐。

**本阶段只负责采集，判据的冻结见主计划 §5。** 采集时必须**按端点类别分开统计**，
因为检索（含外部联邦源）与变体列表（ClickHouse）的成本量级完全不同，
用一个全局阈值覆盖所有端点必然要么误判要么失去意义。

| 端点类别 | 代表端点 | 本阶段采集 |
|---|---|---|
| 检索类（含联邦外部源） | `/api/v1/search` | p50/p95/p99、各源降级率 |
| 详情/列表类（PostgreSQL） | `/api/v1/genes` | p50/p95/p99 |
| 变体列表类（ClickHouse） | `/api/v1/variants`、`/region` | p50/p95/p99、CH `read_rows` |
| 聚合类（有 Redis/未来 CDN 缓存） | `/api/v1/stats/*` | p50/p95/p99、缓存命中率 |

## 4. 风险与回滚

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| 限流未真正关闭 | 开关未生效或边缘未绕过 | 脚本自检 429 必须为 0，否则 exit 1 且不产出报告 |
| `benchmark_mode` 泄漏到生产 | 配置误用 | Phase 1 S-2 已加 prod fail-fast；P1 不额外放宽 |
| 数据量不具代表性 | release 不完整 | 报告必须记录行数；行数不足时标「基线不具代表性」并阻断 Gate-1 |
| 单机 k6 成为瓶颈 | 压测机资源不足 | 记录压测机规格；若 k6 自身 CPU 饱和，标「受压测机限制」并降低 VU 上限 |

**本阶段不产出代码改动**（除 `scripts/perf-baseline.sh` 与 `tests/load/` 扩展），
因此无回滚风险；脚本本身可随时重跑。
