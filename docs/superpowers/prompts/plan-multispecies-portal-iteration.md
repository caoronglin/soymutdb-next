# 任务目标

将 SoyMutDB Next 从“大豆突变体展示与查询系统”迭代为：

1. **多物种科研数据门户**：同一套核心数据模型、页面、搜索和发布流程可支持大豆及后续物种；不复制大豆页面或业务代码。
2. **管理员可治理的平台**：管理员可控制物种、组装、数据发布、页面、内容、导航、模块显示/隐藏、SEO、下载、索引、预览、审核、发布、回滚和审计。
3. **静态优先的公开体验**：公开网站依靠 SSG、CDN/Nginx 与浏览器侧 JavaScript 搜索，保持快速、可访问、可引用；公开页面不直连数据库。
4. **可追溯的发布体系**：每次公开发布都是完整、不可变、可验证和可回滚的快照，页面、导航、下载、搜索索引与数据版本不能错配。
5. **科研友好的 UI/UX**：用户始终知道自己正在看哪个物种、组装与数据版本；搜索、浏览、比较、下载与引用具有明确的科学语境。
6. **可持续演进能力**：技术栈、外部数据源与性能优化通过证据、审核、试点与 ADR 演进，而非盲目追逐最新版本。

# 已引入的项目资料（必须作为规划上下文直接使用）

下列资料是当前项目的已知事实与已有设计方向。不要仅把它们再次列为“待阅读文件”；必须在规划中吸收、校正矛盾并将其落为具体产品决策。

## 资料 A：README.md 已知架构与限制

项目名为 **SoyMutDB Next**，是综合大豆突变体数据库，已有多应用 monorepo 结构：

```text
公开端：apps/web
管理端：apps/admin
后端 API：apps/api
Rust 热路径：apps/core-rs
基因组浏览器：apps/jbrowse
后台 Worker：apps/worker
共享包：packages/ui、packages/i18n、packages/motion、packages/api-client、packages/shared
基础设施：infra/nginx、docker-compose、monitoring
```

现有分层：

```text
Nginx
  /                 → apps/web/dist 的 SSG 静态页面
  /api/v1/*         → FastAPI
  /core/*           → 内部 Rust/Axum 热路径，127.0.0.1:8001
  /admin/           → 仅 localhost / 内网 allowlist 或 Tauri 本地客户端

PostgreSQL          → 用户、内容、组件、业务数据
Redis               → 缓存/锁
ClickHouse          → 匿名分析
```

不可违背的已有边界：

- 公开端为 React + Vite + SSG；前端不能直接访问数据库。
- API 是 FastAPI；管理 API 使用 JWT；管理端应保持 localhost / 内网限制。
- Rust 热路径仅内部访问，且只在有实际性能基准时承担高吞吐搜索、组件渲染和分析写入。
- 动态 HTML 存在多层 XSS 防护：Jinja2 autoescape、bleach、DOMPurify、Trusted Types、CSP、Shadow DOM。
- SQL 使用参数化；密钥只通过环境变量；外部 API 必须限流、缓存和 circuit breaker。
- 当前公开端已有 Web Worker 搜索、View Transition、Web Components、性能观测、CSS Container Queries 和 reduced-motion 方向。
- 性能目标：静态页面低 TTFB、缓存组件 P95 < 50ms、内部 API P95 < 200ms、核心 Web Vitals 均为 Good。
- Node >= 20，pnpm 10；根仓库使用 pnpm/Turbo。API 与 Worker 的 Python 版本、依赖和测试边界不同；管理端含 Web 模式与 Tauri 模式。
- `pnpm review` 是仓库内部的确定性审查，不等同于 Alibaba Open Code Review。

## 资料 B：docs/design/architecture.md 已知设计资产

已有 Widget / PageLayout / Search / SSG / Admin / Analytics 的初步设计：

```text
Widget：名称、分类、模板、数据源、参数 schema、缓存 TTL、管理配置、权限、启用状态
PageLayout：页面名与 widget 顺序
StaticPage：静态内容、双语标题/内容、状态、版本历史
ContentVersion：内容历史快照
Release：现有数据发布实体
```

现有 Widget 方向：

- API 提供布局、组件片段、组件管理、预览、健康度等能力。
- SSG 构建读取页面布局和组件内容，生成 HTML；动态组件可在运行时加载。
- 组件缓存采用内存 + Redis，支持锁与预热。
- 管理端已有 Widgets、Layout、Content、Preview、Health 等分散入口。

现有 Search 方向：

- 后端可聚合 NCBI、UniProt、Ensembl、EMBL-EBI 等外部来源。
- 外部来源应该有 adapter、缓存、超时、重试、限流和 circuit breaker。
- 当前搜索结果可按来源分组，来源可显示 available / degraded / unavailable。

现有 SSG 方向：

- SSG 生成首页、关于、浏览、搜索、样本详情、指南、下载、文献与帮助页面。
- 静态组件构建期生成；动态组件运行期加载。
- 构建后会生成样本页并 gzip 压缩静态资源。

这些是可复用基础，不是最终产品答案。你的规划必须说明：哪些保留、哪些泛化、哪些替换、哪些删除，以及迁移顺序。

## 资料 C：现有路线图中的产品目标与风险

已提出但尚未完整落地的目标包括：

- 控制面与公开数据面分离。
- 发布时静态化：内容、模块、数据、索引在发布快照内一致。
- 物种无关数据内核：`Species → Assembly → DatasetRelease → Gene / Variant / Line / Annotation / Evidence`。
- 管理员有完整业务控制力，但不绕过审计、审批与发布机制。
- 页面与模块使用受 Schema 约束的声明式配置，不建设允许任意脚本的低代码系统。
- 客户端静态搜索按物种、实体类型、语言分片；Web Worker 防止阻塞主线程。
- 技术情报从可信来源采集并经人工审核；不能自动触发依赖升级、部署或公开发布。
- 至少选择一个第二物种，证明多物种架构复用而非复制。
- 每个阶段引入 Alibaba Open Code Review，同时保留构建、测试、安全和人工科研审核。

已知风险必须在规划中逐一处置：

1. 不要混用 `dataset_release_id`（科研数据快照）与 `publication_release_id`（公开门户快照）。
2. 不要先改 UI/搜索再定义多物种数据标识与迁移兼容层。
3. 不要让动态组件读取“最新数据”破坏静态发布一致性。
4. 不要因管理员“全权限”而开放数据库/服务器直连或跳过审计。
5. 不要让静态搜索混淆本地已发布数据与外部实时数据。
6. 不要以服务拆分或最新技术版本为目的；必须以指标和兼容性为依据。
7. 不要把系统清理理解为粗暴运行清理命令；锁文件、有效制品、当前发布快照和其他任务产物都不可误删。

## 资料 D：已有产品体验问题与方向

当前产品仍有明显大豆耦合：首页显示 *Glycine max*、20 条染色体、Wm82 组装；基因页使用大豆染色体常量；主导航及移动导航存在硬编码数据模块入口。现有搜索已有 Gene、Variant、Mutant Line、Expression 等分组基础，但物种、组装、来源、索引版本与外部结果边界尚不足。

已有的管理端结构包含 Data Management、Tools、Presentation、Administration；其中 Releases、Assemblies、Variants、Tracks、Content、Widgets、Layout、Preview、Health 等功能分散。规划应重组为面向任务的工作区，而不是只继续增加菜单。

公开端设计必须采用以下体验原则：

- 全局科研语境是“物种 + 组装 + 数据发布版本”。
- 用户从物种进入、已知 ID 直接搜索、科研探索筛选/比较/导出，是三条核心旅程。
- 物种信息不能仅用颜色或图片表达，必须有徽章、学名、组装与文字状态。
- 多物种详情、下载、浏览器和共享链接要能复现其物种/组装/数据版本。
- 无数据、未发布、维护中、下线和外部源失败必须有明确、可操作的状态。
- 小屏必须可筛选、看详情和清空筛选，不依赖 hover；图表有文字摘要与数据下载。

# 强制规划约束

## 1. 技术与命名规范

- 对技术栈给出“保留 / 升级 / 引入 / 暂缓”的决策表。优先选当前稳定、可维护、与现有 React/Vite/FastAPI/PostgreSQL/Redis/Rust 兼容的技术；每项必须说明版本策略、收益、迁移成本、风险、试点范围、回滚方式。不要只写“使用最新技术”。
- 新增自有函数、变量、模块、类型、组件、服务、脚本和测试夹具统一使用 `rl_` 前缀；第三方 API、框架约定、环境变量、数据库既有列、配置键、路由协议、已有公共接口和已有导出不强行改名。
- 规划必须要求实施者为新增业务规则、权限判断、发布/版本转换、数据清理边界和非直观性能优化写简洁中文“为什么”注释。
- 只能使用仓库根目录 `skills/` 下的 skills。规划中需要列出每项实施任务应使用的 skill 名称与路径；不能假定存在知乎 skill。若没有 `skills/zhihu-*` 或等价能力，技术调研应使用官方来源并记录缺口。

## 2. 版本、发布与打包规范

- `dataset_release_id`：属于一个 `assembly_id` 的科研数据快照，用于 Gene、Variant、Line、Annotation、下载数据和搜索文档。
- `publication_release_id`：公开门户快照，冻结页面、导航、模块、引用的数据发布、静态实体页、下载清单和搜索清单；不能复用现有 `Release.id`。
- 每个发布必须有 `PublicationManifest`，至少记录 manifest schema、输入内容版本、引用的 dataset release、配置哈希、索引/下载 URL 与 SHA-256、构建工具版本、Git commit、不可变产物路径和前一快照。
- 打包链路必须是：已审核内容 + 已验证数据 → 冻结 manifest → Web SSG / Admin / API / Worker / Rust 分别构建 → SBOM + SHA-256 + 测试 + OCR 证据 → `artifacts/manifest.json` → 预览验证 → 原子发布或回滚。
- 每个制品必须有 commit、lockfile 哈希、构建工具版本、SHA-256 和适用的发布快照；发布器不能直接消费工作区文件。

## 3. 安全、治理与清理规范

- 管理员可管理业务内容，但不能直接操作生产数据库或生产文件；高风险操作必须重新认证、审核、审计、可回滚。
- 采用能力权限，而非隐式角色层级；Auditor 永远只读。提交者不能审核自己的高风险变更；单管理员例外必须被显式标记、二次确认并告警。
- 审计应采用事务型 outbox、幂等键、独立保留存储和哈希链；审计投递失败时，发布状态不可切换。
- 清理工作需列出候选、引用分析、影响范围、删除前后验证、回滚步骤。不得默认执行 `pnpm clean` 或 `make clean-all`；不得删除 lockfile、密钥、有效制品、当前发布快照或不属于本任务的产物。

- 前置依赖与受影响系统；
- 具体交付物与建议文件/模块边界；
- 实施步骤；
- 测试、性能、安全、无障碍和数据质量验收；
- 必须使用的 `skills/<name>/SKILL.md`；
- Alibaba Open Code Review 范围；
- 发布/回滚策略；
- 完成定义（DoD）；
- 风险、停止条件和后续依赖。

## H. 质量、安全、验证与运营计划

定义：

- 单元、集成、E2E、迁移、双读、数据质量、契约、视觉/无障碍、性能、离线、安全和回滚测试策略；
- Web/Admin/API/Worker/Infra 分边界命令和环境前提；
- OCR 的固定版本、`OCR_NO_UPDATE=1`、完整 Git 历史、JSON 报告、diff review 与 scan 使用条件；OCR 不替代测试；
- 性能预算：首屏、INP、Long Task、搜索分片大小、内存、缓存命中、构建时长、发布耗时、回滚恢复时间；
- 运维仪表盘、告警、健康检查、发布后观测和事故处理；
- 数据来源、许可证、版本、转换过程和引用可追溯性；
- 清理候选的引用检查、删除门禁和保留策略。

## I. 实施智能体委派包

为每个阶段输出一个可复制的实施智能体提示词。每个提示词必须：

- 明确只实施该阶段，不跨阶段猜测；
- 引用该阶段的前置交付物与验收证据；
- 明确要读取的仓库文件和实际使用的 `skills/` 路径；
- 要求所有新增自有标识使用 `rl_` 前缀、关键逻辑写中文注释；
- 写清允许修改/禁止修改的目录、模块、数据和 API；
- 要求测试先行、构建验证、OCR 审查、制品证据和回滚说明；
- 要求删除无用内容前进行引用分析；
- 以固定格式输出变更、验证、风险、清理和下一阶段交接。
